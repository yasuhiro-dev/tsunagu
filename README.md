# Tsunagu（つなぐ）

保護者面談の日程調整を自動化する、学校向けスケジューリングシステムです。

現役小学校教員としての実務経験をもとに、「兄弟の連続配置」「特別支援学級との調整」といった学校現場特有の複雑な制約を同時に満たすスケジューリングアルゴリズムを実装しています。

## サービス概要

学校現場では、保護者との個人面談の日程調整を教員が手作業で行っています。実際に現場で感じていた課題は次の通りです。

- 全家庭分の面談を、条件を考慮しながら手作業で割り振るのは大きな負担
- 兄弟関係（上の子・下の子が別クラス）や特別支援学級との併籍など、**クラスをまたいだ調整**が必要になるケースが多い
- 既存の日程調整サービスは基本的に「先着順」で、ITに不慣れな家庭や忙しい家庭が不利になりやすく、公平性に欠ける
- 兄弟や特別支援学級がらみの調整機能を持つサービスがほとんど存在しない

そこで本アプリでは、**「全家庭を必ず割り当てる」「学校特有の制約条件を尊重する」** という前提を置き、これらを同時に満たすスケジューリングアルゴリズムを軸とした機能・データ設計を行っています。

### 必須条件

- 全家庭を必ず割り当てる
- 保護者が提出した面談不可日時には割り当てない
- 兄弟は連続した枠に配置する（例：兄が5年3組の枠 → 続けて弟が3年2組の枠）
- 特別支援学級に在籍する児童は、通常学級の面談と連続した枠に配置する
- 面談枠は有限

### 割り当ての優先度制御

制約が強い家庭ほど選べる枠が少なくなるため、**制約の強さをスコア化し、スコアの高い家庭から先に枠を確保する**方式を採用しています。

| 条件                   | スコア | 理由                                                      |
| ---------------------- | ------ | --------------------------------------------------------- |
| 兄弟がいる             | +4     | 連続した2枠が必要。かつクラスをまたぐため最も選択肢が狭い |
| 特別支援学級を含む     | +2     | 通常学級との連続枠が必要                                  |
| 面談不可日時を提出済み | +1     | 選べる枠が減っている                                      |

合計スコアの降順で処理し、条件を満たす枠が見つからなかった家庭は割り当てをスキップして、教員が手動で最終調整します。

## 主な機能

### 保護者

- **ユーザー登録・ログイン・ログアウト**
  登録時に児童を複数人まとめて登録でき、同一家庭に紐づく児童が兄弟として扱われます。
- **面談不可日時の提出**
  提示された面談枠のうち、都合の悪い枠を Web 上で選択して提出します。
- **確定した面談日程の確認**
  割り当て完了後、自分の子どもの面談日時を一覧で確認できます。
- **Googleカレンダーへの登録**
  確定した面談日程を、ワンクリックで自分の Google カレンダーに追加できます。

### 教員

- **面談枠の設定・自動割り当ての実行**
  担当クラスの面談枠を設定し、割り当てアルゴリズムを実行します。
- **担当児童一覧の確認**
  担当クラスの児童と、未割り当ての児童を確認できます。
- **面談スケジュールのPDF出力**
  確定した面談表を、日付 × 時間のマス目形式で PDF 出力します。
- **Googleアカウント連携**
  OAuth 2.0 で Google アカウントを連携します。面談確定時の保護者への通知メールは、連携した教員のアカウントから送信されます。
- **パスワードリセット**

### 管理者

- **教員・保護者アカウントの管理**
  作成・編集・削除に加え、氏名やクラスによる絞り込み、複数選択による一括削除、ページネーションに対応しています。
- **割当状況の可視化**
  クラスごとの割り当て済み・未割り当ての状況をグラフで確認できます。

### 技術選定理由

**バックエンド：Ruby on Rails（APIモード）**

割り当てアルゴリズムという複雑な業務ロジックを持つアプリのため、ActiveRecord によるデータ操作のしやすさと、サービスクラスへのロジック分離のしやすさを重視して Rails を採用しました。View 層を持たない API モードにすることで、フロントエンドの技術選定に制約を持たせず、責務を明確に分離しています。

**フロントエンド：Next.js（TypeScript）**

面談表（時間 × クラスのマス目）や割り当て結果など、状態変化の多い画面を扱うため、コンポーネント単位で状態を管理できる React ベースの Next.js を採用しました。TypeScript により Rails API との通信で扱うデータ構造を型として定義し、フロントエンド・バックエンド間の不整合を防いでいます。

データ取得には SWR を使用し、一覧の再取得やキャッシュ制御を `useEffect` で個別に管理する必要がない構成としています。

**認証：JWTの自前実装**

学習を目的に、gem に頼らず JWT を自前で実装しました。トークンの発行・検証に加え、有効期限（30分）の設定、ロールベースの認可（`authorize_role!`）を各コントローラーに横断的に適用する設計まで含めて実装することで、認証・認可の仕組みそのものへの理解を深めています。

**インフラ：AWS（ECS Fargate + S3/CloudFront）**

個人開発であっても本番運用を想定した構成で設計・運用する経験を得ることを目的に、バックエンドは ECS Fargate、フロントエンドは S3 + CloudFront という構成を採用しました。サーバー管理を意識せずにデプロイできる点と、フロントエンド・バックエンドを独立してスケール・更新できる点を重視しています。

### セキュリティ

本アプリは児童氏名・保護者のメールアドレスといった個人情報を扱うため、以下を実装しています。

- **Google のアクセストークン / リフレッシュトークンを暗号化して保存**
  Active Record Encryption（`encrypts`）により、DB 上でトークンが平文で保存されないようにしています。
- **秘匿情報は Rails credentials で暗号化管理**
  Google OAuth のクライアント ID / シークレット等は `config/credentials.yml.enc` に暗号化してコミットし、復号鍵はリポジトリに含めず環境変数（`RAILS_MASTER_KEY`）として各環境に渡す構成としています。
- **ロールベースの認可**
  `authorize_role!` を各コントローラーの `before_action` に適用し、教員・保護者・管理者それぞれが自分のロールの API しか呼べないよう制御しています。保護者のカレンダー登録では、対象の面談が自分の家庭のものかまで検証しています。
- **CI での脆弱性スキャン**
  Brakeman（Rails の静的セキュリティ解析）と bundler-audit（gem の既知脆弱性チェック）を CI で実行しています。

### テスト・CI/CD

バックエンドでは RSpec によるリクエストスペックとサービススペックを作成し、機能追加や修正時のデグレードを防止できる構成としています。

| 対象                                            | examples    |
| ----------------------------------------------- | ----------- |
| `spec/services/scheduling/`（割り当てロジック） | 23          |
| `spec/requests/api/v1/`（API・認可）            | 89          |
| `spec/mailers/`                                 | 1（未実装） |
| **合計**                                        | **113**     |

特に割り当てアルゴリズムは責務ごとに8クラスへ分割しており、各クラスに対応するスペックを1対1で用意することで、条件を追加・変更した際の影響範囲を局所的に検証できる構成としています。

CI（GitHub Actions）では push / pull request をトリガーに、以下を自動実行しています。

| ジョブ      | 内容                                                |
| ----------- | --------------------------------------------------- |
| `scan_ruby` | Brakeman / bundler-audit によるセキュリティスキャン |
| `lint`      | RuboCop によるコードスタイルチェック                |
| `test`      | MySQL コンテナを起動し、RSpec 113件を実行           |

フロントエンドは ESLint によるチェックを CI で実行しています。

CD では main ブランチへのマージをトリガーに、バックエンドは Docker イメージをビルドして ECR へ push し ECS サービスを更新、フロントエンドは静的ビルドを S3 へ同期して CloudFront のキャッシュを無効化する構成としています。

## システム構成

### インフラ構成図

- フロントエンドとバックエンドを AWS 上で分離構成として構築
- Route53 による DNS 管理、ACM による SSL/TLS 証明書の管理
- バックエンドは ECS Fargate 上で Rails コンテナを実行、DB は RDS（MySQL）
- フロントエンドは S3 + CloudFront で静的配信
- GitHub Actions から ECR への push / ECS サービス更新、および S3 同期を自動化

### ER図

- `Child`（児童）と `ClassRoom`（クラス）は、特別支援学級との併籍を考慮し、中間テーブル `child_class_rooms` を介した**多対多**の関係で設計
- `User` は `role`（teacher / parent / admin）に応じて、`after_create` コールバックで自動的に `Teacher` または `Family` レコードを生成し、認証情報と業務データの整合性を保証
- `Assignment` が `Child`（児童）と `MeetingSlot`（面談枠）を結びつけるモデルとして、割り当て結果を保持
- `FamilyUnavailability` が家庭ごとの面談不可枠を保持し、割り当て時のフィルタ条件として使用

## 設計で工夫した点

### 割り当てロジックの責務分割

このプロジェクトの技術的な核となるのが、複数の制約条件を同時に満たす割り当てロジックです。単一の巨大な処理として実装するのではなく、単一責任原則を意識して責務ごとにサービスクラスへ分割しています。

```
app/services/scheduling/
├── group_children.rb      # 兄弟・特別支援学級でグループ化
├── priority_sort.rb       # 制約の強さをスコア化して並び替え
├── schedule_assigner.rb   # 全体のフローを制御するメイン処理
├── available_slots.rb     # 担当教員の空き枠を取得
├── time_filter.rb         # 保護者が提出した面談不可枠を除外
├── siblings_filter.rb     # 兄弟が連続で入れる枠に絞り込み
├── support_filter.rb      # 特別支援学級との連続枠を考慮
└── assigner.rb            # 実際の割り当て（Assignmentレコード作成）
```

**処理の流れ**

1. `GroupChildren` が児童を家庭単位でグループ化し、兄弟・特別支援学級の在籍状況に応じて構成を組み立てる
2. `PrioritySort` が各グループの制約の強さをスコア化し、降順に並び替える
3. `ScheduleAssigner` が各グループについて、`AvailableSlots` → `TimeFilter` → `SiblingsFilter` → `SupportFilter` の順にフィルタを通す
4. 残った枠があれば `Assigner` が割り当てを確定。空になった場合はスキップし、教員が手動で調整

フィルタを1クラス1責務に分割したことで、それぞれを独立してユニットテストでき（`spec/services/scheduling/` に23 examples）、条件の追加・変更にも対応しやすい設計にしています。

### 制約の強さをスコア化した優先度制御

割り当ての順番は、結果の充足率を大きく左右します。選べる枠が少ない家庭を後回しにすると、その家庭だけ空き枠が残らず未割り当てになるためです。

当初は「兄弟 → 特別支援 → 時間指定あり」と条件ごとに段階的に処理する実装を検討しましたが、複数条件を同時に満たす家庭（兄弟がいて、かつ特別支援学級に在籍している等）の扱いが曖昧になる問題がありました。

そこで、条件を排他的な分岐ではなく**加点方式のスコア**として扱い、合計値の降順で一括ソートする方式に変更しました。

```ruby
def score(group)
  score = 0
  score += 4 if siblings           # 連続2枠 + クラスまたぎ
  score += 2 if has_support        # 通常学級との連続枠が必要
  score += 1 if has_unavailable    # 選択可能な枠が減っている
  score
end
```

これにより、複合条件を持つ家庭が自然に最優先（最大7点）となり、条件の追加もスコアの加点ルールを1行足すだけで済む構成になりました。

### 多対多関係によるクラス設計

児童が複数のクラス（通常学級と特別支援学級の併籍など）に所属しうるという学校現場特有の事情を踏まえ、`Child` と `ClassRoom` は中間テーブル `child_class_rooms` を介した多対多の関係で設計しました。

`children` テーブル自体にクラス関連のカラムを持たせていないため、併籍パターンが増えてもスキーマ変更が不要で、`child.class_rooms` という関連付けメソッド経由で柔軟にクラス情報を取得・更新できます。割り当てロジックが「この児童は特別支援学級に在籍しているか」を判定する際も、`child.class_rooms.where(room_type: "support")` という形で素直に表現できています。

## 苦労した点・学んだこと

### RSpecが開発用DBに接続してしまう問題の原因調査

RSpec 実行時に、テスト用DB（`interview_app_test`）ではなく開発用DB（`interview_app_development`）に接続してしまい、テストの結果が実行のたびに変わる問題が発生しました。

`spec/rails_helper.rb` には `ENV['RAILS_ENV'] ||= 'test'` という記述があり、一見すると `test` 環境が設定されるように見えました。しかし `||=` は「値が未設定のときだけ代入する」演算子です。実際には `Dockerfile.dev` 側で以下のように環境変数が明示的に指定されており、Docker イメージのビルド時点で `development` が固定されていました。

```dockerfile
ENV RAILS_ENV="development"
```

このため `||=` による代入は最初から実行されず、開発用DBを見に行っていました。

原因を特定した後は、RSpec 実行時に `RAILS_ENV=test` を明示的に渡すことで解決しました。また、同じ長いコマンドを繰り返し打つ手間を減らすため、`bin/test` という実行用スクリプトを作成しています。

```bash
#!/usr/bin/env bash
RAILS_ENV=test bundle exec rspec "$@"
```

この経験から、環境変数は「アプリケーションのコードのどこで設定されているか」だけでなく、「Docker のビルド時点で固定されていないか」まで含めて確認する必要があることを学びました。設定の優先順位を意識せずに `||=` のような記述を信用すると、原因の特定に時間がかかります。

### PDF出力機能でのPuppeteer導入トラブル

面談表を PDF 出力する機能を Grover（Puppeteer）で実装する際、開発環境で 500 エラーが発生しました。調査の結果、2つの原因が重なっていました。

1. `Dockerfile.dev` で `npm install` が実行されておらず、Puppeteer の node_modules が存在しなかった
2. `docker-compose.yml` の volume 設定により、コンテナ内の `node_modules` がホスト側の空ディレクトリで上書きされていた

また Puppeteer は既定で Chromium を自動ダウンロードしますが、これはイメージサイズと起動時間の両面で不利なため、`apt` で導入した Chromium を使う方針に変更しました。最終的に `Dockerfile.dev` を以下のように修正し、volume 設定で `node_modules` を除外することで解消しました。

```dockerfile
ENV PUPPETEER_SKIP_DOWNLOAD=true
ENV PUPPETEER_SKIP_CHROME_DOWNLOAD=true
RUN npm install
```

なお本番環境（ECS Fargate）については、Chromium と Node.js は Dockerfile に導入済みですが、`npm install` の実行を本番ビルドに反映する作業が残っています。現在対応中です。

この経験から、コンテナ環境では「ライブラリを入れる」だけでなく、それが実行時にどこから読み込まれるか（volume でマウントが上書きされていないか）まで確認する必要があることを学びました。

## リポジトリ構成

本プロジェクトは、バックエンド・フロントエンド・Docker Compose 設定を分離した**マルチリポジトリ構成**です。

📍 **このページ（`tsunagu`）が起点です。** まずこの README でプロジェクト全体を把握した上で、必要に応じて各リポジトリのコードをご覧ください。

| リポジトリ                                                             | 役割                                                    | 規模            |
| ---------------------------------------------------------------------- | ------------------------------------------------------- | --------------- |
| **[tsunagu](https://github.com/yattinx-tech/tsunagu)（本リポジトリ）** | プロジェクト概要・Docker Compose によるローカル統合環境 | —               |
| [tsunagu-backend](https://github.com/yattinx-tech/tsunagu-backend)     | Rails API（バックエンド）                               | 250コミット以上 |
| [tsunagu-frontend](https://github.com/yattinx-tech/tsunagu-frontend)   | Next.js（フロントエンド）                               | 130コミット以上 |

実装の大半は `tsunagu-backend` と `tsunagu-frontend` にあります。割り当てアルゴリズムは `tsunagu-backend` の `app/services/scheduling/` をご覧ください。

### なぜマルチリポジトリ構成にしたか

モノレポではなくマルチレポを選んだ理由は、バックエンド・フロントエンドそれぞれで独立した CI/CD パイプラインを組み、デプロイのタイミングを分けられるようにするためです。実際、バックエンドは ECR / ECS、フロントエンドは S3 / CloudFront と、デプロイ先も手順も異なります。Git 履歴やブランチもリポジトリごとに独立するため、片方の変更履歴だけを追いたい場合に見やすくなります。

一方で、複数リポジトリに分かれていることで全体像を把握しづらくなるという弱点があります。その弱点を補う目的でこの `tsunagu` リポジトリを「入口」として位置づけ、プロジェクト概要・技術構成・スクリーンショット・各リポジトリへのリンクをここに集約する構成にしています。

## ローカル環境の立ち上げ方

`docker-compose.yml` はバックエンドを `interview_app`、フロントエンドを `meeting_front` というディレクトリ名で参照します。**この `tsunagu` ディレクトリの中に**、その名前でクローンしてください。

```bash
# 1. 起点となるリポジトリをクローンして移動
git clone https://github.com/yattinx-tech/tsunagu.git
cd tsunagu

# 2. バックエンド・フロントエンドを指定のディレクトリ名でクローン
git clone https://github.com/yattinx-tech/tsunagu-backend.git interview_app
git clone https://github.com/yattinx-tech/tsunagu-frontend.git meeting_front

# 3. Rails credentials の復号鍵を .env に配置
echo "RAILS_MASTER_KEY=<マスターキー>" > .env

# 4. コンテナを起動
docker compose up -d

# 5. DBのセットアップ
docker compose exec rails_container bin/rails db:create db:migrate db:seed
```

| URL                   | 内容                      |
| --------------------- | ------------------------- |
| http://localhost:3001 | フロントエンド（Next.js） |
| http://localhost:3000 | バックエンド API（Rails） |

テストの実行：

```bash
docker compose exec rails_container bin/test
```
